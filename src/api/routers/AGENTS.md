# routers

One `APIRouter` per concern, all mounted by `../main.py`. Each router does the session check through `get_current_user` (API) or `get_current_user_from_session` (pages) from `../auth_routes.py`, talks to Postgres through `SessionLocal` and to the DuckDB warehouse through `get_db_connection` in `../deps.py`.

- `pages.py`: the server-rendered pages (`/dashboard`, `/training-calendar`, `/warehouse`, `/workout_streams/{id}`, `/profile`, `/races/{id}/pacing`). Markup only; data comes from the API routers below. The activity page hides the Strava link for imported activities.
- `activities.py`: synced and imported activities: list (each row carries `structure_kind` and `structure_checked` from the structure pass), per-user list, detail, streams, laps (the watch's splits), detected intervals (`GET /api/activities/{id}/intervals`), effectiveness, AI note, delete (`delete_activity_rows`: the tables in `src.pipeline.ACTIVITY_CHILD_TABLES`, then `dim_activity`).
- `imports.py`: `POST /api/activities/import`, multipart FIT/GPX upload (up to 20 files, 25 MB each); returns one result per file (`imported`, `skipped` with the reason, or `error`). The work is in `../services/imports.py`.
- `sync.py`: start a background Strava sync and read its progress (`src.api.services.sync`). `start_sync_for(user)` is the one place that builds a user's sync job; the webhook uses it too. `record_sync_result` stores the new token and then marks matching planned sessions done (`services/plan_match.py`).
- `strava_webhook.py`: Strava's push subscription at `/api/strava/webhook/{token}`, where the token is `STRAVA_WEBHOOK_VERIFY_TOKEN`; any other path is a 404, because Strava does not sign events. `GET` answers the subscription handshake; `POST` takes activity create/update (queue a sync), delete (remove from the warehouse) and athlete deauthorization events. `scripts/strava_webhook.py create <site>` registers the subscription with the token in the path.
- `workouts.py`: the workout library CRUD.
- `analytics.py`: training status (with the coach's note), VO2 max, pace zones, dashboard analytics (HR zones, time by type, weekly volume), race predictions from best efforts with the VDOT ceiling (`/api/predictions`), aerobic efficiency on easy runs (`/api/efficiency`), personal records (`/api/records`).
- `races.py`: races CRUD.
- `profile.py`: profile updates and `GET /api/hr-profile/{user_id}` (resting and max heart rate in use, and where they come from; `detected_max_hr` is null without heart rate data, `default_max_hr` is the fallback). A changed heart rate profile queues a metrics recompute, after any job already running.
- `plan.py`: training plan entries CRUD; `GET /api/projection/{user_id}`: fitness, fatigue and form stepped forward along the planned sessions (load per session from the athlete's TRIMP per kilometre scaled by workout type), with upcoming race dates; `POST /api/training-plan/{user_id}/build`: fills the calendar from tomorrow to a race with entries from `src/plan_builder.py`, starting from the last four weeks of run volume in the warehouse unless the body gives a weekly distance.
- `digest.py`: weekly digest email settings (`GET`/`POST /api/digest/{user_id}`), `GET .../preview` for the text the user would get, and `POST .../send` to send it now.
- `coros.py`: the COROS link: `GET /api/coros/{user_id}` status, `POST .../link` (logs in with email and password, keeps only the token, pulls a year of nights), `POST .../sync`, `DELETE /api/coros/{user_id}`, `GET /api/recovery/{user_id}` with the nightly HRV, resting heart rate and time in bed for the dashboard, `GET /api/readiness/{user_id}`: today's Go / Normal / Easy / Rest call from this morning's energy and its trend, with the reasons and a hint when today's planned session is hard, and `GET /api/energy/{user_id}?days=7` (1 to 14): the energy curve hour by hour with the nights that charged it, the activities that drained it and today's call (`services/readiness.energy_for`). Both answer `{"available": false}` without COROS nights. `../main.py` mounts this router only when `COROS_ENABLED` is not `false`, so every one of these routes answers 404 on an install with COROS switched off.
- `pacing.py`: `GET /api/races/{race_id}/pacing?goal&strategy&unit` builds the split plan from `src/pacing.py` (goal from the query, else the race, else the Riegel prediction via `analytics.recent_best_efforts` and `predict_from_efforts`); `POST`/`DELETE /api/races/{race_id}/course` store or drop the course GPX on the race.

A new endpoint goes in the router that owns its data; a new concern gets a new file here and one `include_router` line in `main.py`.
