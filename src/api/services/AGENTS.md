# services

Logic the routes in `../main.py` call, kept out of the route file.

- `metrics.py`: training status from the DuckDB warehouse: daily load to CTL/ATL/TSB/ACWR (`load_history(con, athlete_id, today)` is the day-by-day frame, also read by `insights.py`; `EASY_RUN_SQL` is the one definition of the dashboard's easy runs) with a 14-day fitness projection (`acwr_ready` says whether the history, first activity to today, reaches `ACWR_HISTORY_DAYS`, 28; before that the ratio has no chronic side and the dashboard does not show it), VO2 max estimates, pace zones around a threshold speed (`pace_zones_from_threshold_speed` is the pure part).
- `imports.py`: `import_files(db, user, files)` parses each `(filename, bytes)` with `src.importers`, skips a file already imported or starting within 60 s of an existing activity of the athlete, writes the rest (creating a `dim_athlete` row for a file-only user), then runs the structure, effectiveness, best-effort and training-load passes once. `move_to_strava_athlete` is what the Strava callback calls to move a file-only user's rows; `move_athlete` moves `dim_activity`, every table in `src.pipeline.ACTIVITY_CHILD_TABLES` and `coros_daily` in committed steps through `move_*` staging tables, because DuckDB checks foreign keys against committed rows only.
- `sync.py`: background jobs with progress, one live job per user. `sync_job(user_id)` (kind `sync`, `src.pipeline.sync_athlete`) and `recompute_job(user_id)` (kind `recompute`, `src.pipeline.recompute_metrics`) read the user's token and heart rate profile when they start, not when they are queued. `registry.start` raises `SyncAlreadyRunning` while a job runs (the Sync button); `start_or_queue` keeps one run waiting for when it ends (webhooks, `queue_recompute` after a heart rate change), and a waiting sync covers a later recompute. `SyncJob.snapshot()` is what `GET /api/sync-strava/{user_id}` returns and the browser polls. Progress phases: auth, listing, streams, laps, structure, metrics, load.
- `plan_match.py`: after each sync and each file import, `auto_complete_plan(user_id, athlete_id)` marks the last seven days' planned sessions done and links the run when it matches: Intervals/Tempo by detected structure, Long Run by 80% of the planned distance or the week's longest run, Easy Run/Race by any run, Cross Training/Strength by any activity. `complete_matching_entries(db, con, ...)` is the testable core.
- `email.py`: `send_email(to, subject, body, html)` over SMTP from the `SMTP_*` variables: the text, with the HTML as its `multipart/alternative` when given; with no `SMTP_HOST` it prints the text to the server log instead.
- `digest.py`: the Monday morning email. `compose_digest` is the pure text builder (last week against the week before, plan compliance, fitness and form, this morning's energy with today's call and its reasons, nightly recovery averages, new best efforts, this week's sessions, upcoming races) and `digest_html` renders the same arguments through `templates/email/digest.html` (a meaning under the form label, energy reasons split into amount and text); `build_digest(db, user, now)` returns the subject, text and HTML, gathers the values from the warehouse and Postgres for one user, and counts a planned session done when the dashboard's week card does (`session_done` over `runs_on_foot`: ticked, or a run that day, but not an Intervals or Tempo day whose analysed runs have another structure); `send_due_digests` is the scheduler pass that sends to opted-in users whose digest is due and stamps `digest_sent_at`.
- `coros_sync.py`: the COROS link. `sync_coros` pulls the nights since the last sync (a year on the first) into `coros_daily`, stamps the user, records failures on `coros_error`, and when the 14-night median resting heart rate moves by 2 bpm or more from `users.coros_resting_hr` stores the new value there and, without a typed resting heart rate, calls `recompute()` (the routes pass `queue_recompute`); `unlink_coros` forgets the session and the nights; `sync_due_coros` is the scheduler pass (once a day after 05:00, skipped while the session is marked expired).
- `readiness.py`: `energy_for(con, athlete_id, now, days, planned_workout)` reads the COROS nights (with the four weeks before the window for the baselines) and each activity's start, elapsed time and TRIMP, runs `src.energy`, and adds today's call from `src.readiness` with the session hint. `{"available": False}` without a COROS reading in the window; `call` is None when the newest reading is more than two days old. Feeds `/api/energy`, `/api/readiness` and the digest.
- `insights.py`: `insights_for(db, user, unit, today)` reads one user's values for the rules of `../../insights.py`: the dashboard's easy runs of the last 28 days (without detected tempo runs, treadmill runs and races) and the zone time of all runs, the efficiency points of the last 84 days with their climb, the COROS nights, `metrics.load_history`, and the last 14 days' planned sessions done as `digest.session_done` counts them. Returns the ranked insights.
- `course_library.py`: the race-courses dataset on GitHub (`RACE_COURSES_URL` points it at a stand-in in tests). `entries()` reads its `index.json` at most once a day for every user: one entry per event of every race, with or without a course; when a later read fails the old copy stays in use, and without one it raises `LibraryUnavailable`. `courses()` is the entries with a course file (`has_course`: status ok, warn or stale). `course_entry(race, event)` is one published course's entry. `course_file(race, event)` fetches only a file that the index lists, so a request cannot make the server fetch another URL, and keeps it in memory for a day (`files`), since the public course pages read the same files again and again; None when the index does not list it. `attach(race, race_slug, event_slug)` stores that course on a `Race` row and returns the parsed course, or None (logged) when there is no course or the library cannot be read, so creating a race never fails on it.
- `admin.py`: the admin page's numbers. `activation(rows, now)` is the pure part: from one row per user (`created_at`, `last_seen_at`, `connected`, `has_race`, `has_course`) the sign-up cohorts of the last 8 weeks (Monday to Sunday, oldest first) and the all-time totals, each with how many connected data, added a race, have a course file and came back (seen 7 days or more after sign-up); a user without `created_at` is in no week but in the totals, counted as `before_tracking`. `user_facts(db, con)` reads those rows from Postgres and the warehouse (connected: a Strava id, `coros_linked_at`, or an activity under the user's `athlete_id`); `recent_feedback(db)` lists the newest 50 notes with the writer's name and email.
- `scheduler.py`: `start_scheduler(jobs)` runs the passes above every half hour from a daemon thread started in `main.py`'s lifespan; the first pass is one interval after start.
- `account.py`: `delete_account(db, con, user, password, revoke)` checks the password with `auth_routes.verify_password` (`WrongPassword` deletes nothing), then removes the warehouse rows under `user.athlete_id` (`delete_warehouse_rows`: every table in `src.pipeline.ACTIVITY_CHILD_TABLES` through the athlete's activities, then `ATHLETE_TABLES`, each statement committed on its own for DuckDB's foreign key checks), the plan entries, plans, races, feedback notes and the user row, and last revokes a stored Strava token through `revoke` (`revoke_strava`: refresh the access token, then `POST /oauth/deauthorize`), best effort. Tests pass a stand-in `revoke`.
- `metrics.py` also owns `coros_resting_hr` (the live 14-night median), `resolve_resting_hr(user)`: the profile value, else `users.coros_resting_hr` as the last COROS sync stored it, else `DEFAULT_REST_HR`, and `recorded_max_hr` (None without heart rate data) under `detected_max_hr` (falls back to `DEFAULT_MAX_HR`). Every route that feeds the heart-rate-reserve model goes through `resolve_resting_hr`.

`../deps.py` owns the DuckDB connection and shared defaults so these modules never import `main.py`.
