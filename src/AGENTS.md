# src

The data side of Race Planner: ingestion into the DuckDB warehouse, the training math, and the plan generator. The web app lives in `api/`.

- `pipeline.py`: Strava client (`StravaManager`), the warehouse schema and writes (`StravaDB`), and the sync passes: `ingest_data` (activities, streams, laps), `run_analyze_effectiveness` (per-activity TRIMP, decoupling, zones), `run_best_efforts`, and `sync_athlete`, which runs them in order (with the structure pass after the laps backfill) and reports progress.
- `metrics.py`: pure functions with no I/O: Banister load model (CTL/ATL/TSB), heart-rate reserve zones, the VO2 max estimator with the ACSM grade cost (`flat_equivalent_speed`, also used by the interval detector), Daniels VDOT and race equivalents, best efforts with Riegel predictions, and the planned-load projection used by the calendar.
- `intervals.py`: pure interval and tempo detector. `detect_structure(time_s, velocity_mps, altitude_m, heartrate)` resamples to 1 Hz, grade-adjusts with `metrics.flat_equivalent_speed`, smooths, splits the moving seconds into fast and slow with two-means, labels with hysteresis, folds short segments, refines rep edges on the raw pace, and calls the run intervals, tempo or nothing. The module docstring lists every threshold.
- `structure_pass.py`: the warehouse side. `run_detect_structure(db, progress)` runs the detector on every run not looked at since its last sync and stores `activity_structure` (one row per run, kind NULL when nothing was found) and `activity_intervals` (one row per rep); `stored_structure(con, activity_id)` reads them back for the API.
- `plan_builder.py`: deterministic training plan generator. `build_plan` returns one entry per day from a start date to race day, with weekly volume ramped from the athlete's current distance toward a race-specific peak, cutback weeks and a taper; `summarize` describes a plan for the confirmation toast. `api/routers/plan.py` writes its output into the calendar.
- `coros.py`: client for the private COROS Training Hub API: `login` (MD5 password, returns the session token and user id), `CorosClient.daily` (nightly resting heart rate, HRV and baseline, training load, in 90-day chunks; no sleep duration, see the docstring) and `verify`. `COROS_API_BASE` points it at a stand-in server in tests. The API is unofficial and can change; errors are `CorosError` / `CorosAuthError`.
- `scrape_coros_workouts.py`: standalone Playwright scraper that reads structured workouts from the COROS web app into the warehouse. Not used by the web app.

Unit tests for all of this are in `../tests/`.
